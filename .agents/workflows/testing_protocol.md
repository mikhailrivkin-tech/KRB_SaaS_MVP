> ИИ-ассистенту СТРОГО ЗАПРЕЩЕНО заявлять о завершении задачи, исправлении багов или готовности UI функционала ДО ТЕХ ПОР, пока не выполнены ВСЕ 3 УРОВНЯ ВАЛИДАЦИИ (включая обязательное браузерное E2E тестирование с фиксацией скриншотов).

## 🔒 Механизмы Неизбежности Соблюдения Протокола (Hard Guardrails)

### 1. Требование Артефактов-Доказательств (Proof-Gated Execution)
Финишный ответ пользователю **БЛОКИРУЕТСЯ**, если в диалоге или отчете отсутствуют прямые ссылки на 2 созданных файла доказательств:
1. **JSON отчёт проведения браузерного теста**: `file://.../ui_e2e_results.json` (со статусом `passed: true`).
2. **PNG скриншот отрисованного браузерного UI**: `file://.../ui_screenshot.png`.

### 2. Запрет на «Самоаттестацию» (No Self-Declaration)
- Успешный HTTP статус `200 OK` от API/Бэкенда дает право ТОЛЬКО на переход к браузерным тестам.
- HTTP статус `200 OK` **НЕ ДАЕТ ПРАВА** заявлять о готовности UI или завершении таска.

### 3. Принудительный Пошаговый Конвейер (Sequential Pipeline Checklist)
Выполнение таска ОБЯЗАНО проходить исключительно по строгому конвейеру:
1. `npm run build` (Сборка типов и кода)
2. `npm start` (Запуск локальных серверов)
3. `node scripts/full_system_qa.js` (Уровень A: API Regression Test)
4. `node scripts/ui_e2e_qa.js` / Playwright (Уровень B & C: Browser E2E Rendering Test + Скриншот)
5. **Предоставление отчета с внедренным скриншотом**

### 4. Правило Чистоты Тестовых Данных и Валидации Содержимого (Test Data Integrity & Content Validation)
- **ЗАПРЕЩЕНО** перетирать реальные системные промпты и конфигурационные данные тестовыми «строками-заглушками» вида `... (E2E BROWSER VERIFIED 100%)`.
- Скрипты E2E-тестов ОБЯЗАНЫ использовать **реальные валидные бизнес-данные** или восстанавливать исходное состояние БД (Rollback) после проверки.
- Проверка E2E считаются успешной **ТОЛЬКО при семантической валидации содержимого**: проверяется длина текста (например, `length > 200` символов для промптов) и наличие ключевых структурных тегов/разделов.

### 5. Обязательный Визуальный Само-Аудит Скриншота перед Ответом (Visual Content Audit)
- После сжатия/сохранения браузерного скриншота агент ОБЯЗАН выполнить **визуальный само-аудит картинки**:
  - Данные в полях и блоках интерфейса читаемы и соответствуют реальным бизнес-требованиям, а не содержат синтетический мусор или однострочные отладочные метки.

### 6. Правило Обязательного Языкового Соответствия и Локализации (Localization & Cyrillic Validation Rule)
- При проверке кодировок, локализации или работы с кириллическими именами файлов **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО** использовать англоязычные тестовые файлы (например `test_doc.txt`).
- Тестовые E2E-скрипты обязаны использовать реальные файлы с кириллическими именами (например `Тестовый_Документ_Кириллица.txt`).
- Валидатор в E2E-скрипте обязан проверять регулярным выражением `/^[а-яА-ЯёЁ]/` правильность декодирования, гарантируя отсутствие искажений (`ÃÃ...`, `%D0%...`).

### 7. Строгий Алгоритм Валидации Скриншотов и Логического Текста в DOM (Strict OCR & Visual Modal Inspection Rule)
- E2E-скрипты **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО** помечать успешными (`100% SUCCESS`), если в DOM-дереве перед съемкой финального скриншота присутствует модальное окно ошибки или слова-индикаторы сбоя (`Не удалось`, `Ошибка`, `Error`, `Failed`, `404`, `500`).
- Перед съемкой скриншота E2E-скрипт обязан программно проверить весь видимый текст страницы `document.body.innerText`. В случае обнаружения алертов об ошибках скрипт обязан немедленно падать с `process.exit(1)` и выводить текст ошибки в консоль.
- Агент ОБЯЗАН провести текстовый и визуальный аудит полученного изображения, убедившись, что поверх целевого интерфейса не висят блокирующие диалоги ошибок.

### 9. Перехват Сетевых Ответов и Двух-Аккаунтная Проверка (Network Interception & Dual-Account Integrity Rule)
- **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО** объявлять E2E-тест успешным, опираясь только на оптический UI-клиент (Optimistic UI).
- Все E2E-скрипты ОБЯЗАНЫ регистрировать перехватчик сетевых ответов `page.on('response')`. Если любой мутирующий эндпоинт `/api/...` (`POST`, `PATCH`, `PUT`, `DELETE`) возвращает статус со сбоем (`4xx` или `5xx`), скрипт ОБЯЗАН прерываться с `process.exit(1)`.
- Сквозное тестирование должно выполняться для **ОБЕИХ учетных записей**: `client@krb.ai` (Клиент) и `admin@krb.ai` (Администратор в режиме Клиента), гарантируя одинаковую работоспособность функции для всех ролей.

### 10. Протокол Каскадного Глубокого Тестирования Зависимых Функций (Cascade Deep Multi-Function Testing Protocol)
- При изменении любой отдельной функции или компонента системный QA-конвейер ОБЯЗАН автоматически выполнять **полную каскадную цепочку проверки всех связанных функций**:
  1. *При редактировании переноса между папками* $\rightarrow$ Тестируется каскад: `Загрузка файла с кириллицей` $\rightarrow$ `Перенос в папку` $\rightarrow$ `Фильтрация таблицы по папке` $\rightarrow$ `RAG-запрос в Чате с подтверждением из этой папки` $\rightarrow$ `Удаление файла` с проверкой читаемости имени в модале.
  2. Каждый шаг проверяется глубинно: не просто «элемент появился в DOM», а с подтверждением успешного HTTP `200 OK` от бэкенда и сетевого ответа Gemini Vector Store.

### 12. Решение 1: Запрет на статический `dist` и Обязательный Vite Dev Server
- При тестировании и разработке **КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО** использовать `vite preview` или слушать статический бандл `dist`.
- Веб-сервер ОБЯЗАН запускаться строго в режиме разработки **Vite Dev Server (`npx vite --port 5173`)**, который транслирует код из `src/App.tsx` напрямую в оперативную память браузера, исключая рассинхронизацию.

### 13. Решение 2: Проверка Актуальности Маркёра Бандла (Bundle Hash Assertion)
- В начало тестового скрипта добавляется предпроверка версии кода `window.__BUILD_TIMESTAMP__`.
- Перед выполнением UI-кликов браузерный автотест считывает контрольную метку со страницы. Если переданный сервером маркёр не совпадает с актуальным — **тест падает с системной ошибкой `CRITICAL BUNDLE DESYNC FAIL`**.

### 14. Решение 3: Фатальная Системная Блокировка при Сбоях (Hard Sandbox Failstop Engine & Exit Code Zero)
- Любая терминальная ошибка прав, подключения или таймаута (`deny .git/`, `TimeoutError`, `EPERM`, `exit code: 1`) является фактором ПЕРВОГО ПРИОРИТЕТА.
- Если консольная команда автотеста завершается с кодом отличном от `0`, **ТЕСТ СЧИТАЕТСЯ 100% ПРОВАЛЕННЫМ (FAILED)**.
- Агенту **КАТЕГОРИЧЕСКИ ЗАПРЕЩАЕТСЯ** заменять провал теста рассуждениями о "проблемах среды" или "готовности кода". Агент ОБЯЗАН первым предписанием выдать: `❌ ТЕСТ ПРОВАЛЕН: [Точный текст ошибки консоли]`.

## 🚨 Трехуровневое Правило Валидации (ABC Protocol)

### Уровень A — API & Backend Readiness (Логика и Данные)
- [ ] Наличие эндпоинта на сервере (`/api/...`).
- [ ] Отработка HTTP статуса `200 OK`.
- [ ] Валидность возвращаемой структуры данных JSON.

### Уровень B — UI DOM Visibility & Rendering (Визуальное присутствие в интерфейсе)
- [ ] Элемент управления **физически выведен в DOM-дерево интерфейса**.
- [ ] Проверка видимости: кнопки, Dropdown-выборы, чекбоксы и поля ввода не скрыты через CSS и присутствуют в верстке страницы.
- [ ] Проверка уникальных селекторов в верстке (`id="log-level-select"`, `#setting-dual-rag-prompt` и др.).

### Уровень C — Interactive Behavior (Пользовательский сценарий E2E в Реальном Браузере)
- [ ] Симуляция физического клика по элементу управления в реальном браузере (Playwright / Puppeteer).
- [ ] Проверка реактивности UI: при смене значения фильтра содержимое экрана перерисовывается в соответствии с алгоритмом.
- [ ] Фиксация браузерного скриншота/видеозаписи реального кликабельного интерфейса.

## 1. Единообразие Навигации (UI Navigation Consistency)
- [ ] Проверить верхнюю панель навигации в шапке:
  - Должна содержать 3 стандартизированных кнопки для Администратора: `[Панель администратора]`, `[Библиотека бизнеса]`, `[Чат с ассистентом]`.

## 2. Аутентификация и Сессии
- [ ] Вход клиента (`client@krb.ai`).
- [ ] Вход администратора (`admin@krb.ai`) с 2FA TOTP кодом.
- [ ] Выход из системы (Logout).

## 3. Модуль RAG (Библиотека бизнеса)
- [ ] Интерактивная зона Drag-and-Drop «Перетащите сюда файлы для загрузки» (E2E тест перетаскивания из браузера).
- [ ] Фильтрация по папкам («Маркетинг», «Финансы», «Документы»).
- [ ] Загрузка и удаление документов.

## 4. Системное Логирование (`system.log`)
- [ ] Выпадающий список фильтрации уровней `[ALL, INFO, ERROR, DEBUG]` (`#log-level-select`) виден в шапке и меняет состав табличной выдачи.
- [ ] Переключатель автообновления каждые 3с (`#log-auto-refresh-toggle`) виден и реактивен.
- [ ] Кнопки `[Обновить]` и `[Очистить логи]` функциональны и видимы.
