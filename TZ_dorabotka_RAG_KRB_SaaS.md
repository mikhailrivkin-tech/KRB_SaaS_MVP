# ТЗ на доработку: устранение проблем поведения RAG-чата KRB SaaS MVP

**Контекст:** данный документ — ТЗ на доработку уже реализованного MVP (см. `TECHNICAL_SPECIFICATION.md`), закрывающее проблемы, зафиксированные в `RAG_PROBLEMS_AND_REQUIREMENTS.md`. Цель — привести поведение системы к паритету с нативным RAG-чатом Google (Gemini app / NotebookLM): предсказуемость, скорость на простых репликах, отсутствие "фантомных" данных, корректная диагностика сбоев.

---

## 0. Приоритет №1: Исключить каскадный фоллбек между разными моделями

### Проблема
Текущая реализация (`TECHNICAL_SPECIFICATION.md`, п. 3.3.4) при сбое или таймауте одной модели автоматически переключается на другую (`gemini-2.0-flash` → `gemini-2.5-flash`). Модели разного поколения дают разное качество и стиль ответа на один и тот же вопрос — клиент получает непредсказуемо разный результат в зависимости от того, ответила ли основная модель вовремя. Это неприемлемо для консультационного продукта, где стабильность и предсказуемость ответа важнее отказоустойчивости за счёт подмены модели.

### Требование
1. **Убрать автоматическое кросс-модельное переключение полностью.** Запрос всегда идёт к одной, явно заданной модели.
2. **Выбор модели — явная настройка в админке**, не хардкод в коде:
   - Глобальная настройка по умолчанию (в разделе "Настройки" или "Боты").
   - Возможность переопределить модель для конкретного бота (если разным ботам нужна разная модель — например, более дешёвая для простого FAQ-бота и более мощная для сложного консультанта).
3. **Retry оставить, но только на той же модели.** Если модель не ответила из-за сетевого сбоя/таймаута — повторный вызов идёт **той же самой** модели, не более 2–3 раз, с коротким интервалом. Если все попытки исчерпаны — пользователь видит явную ошибку (см. п. 6), а не тихую подмену на другую модель.
4. Если администратор хочет явно настроить резервную модель на случай полной недоступности основной — это допустимо, но **только как осознанный выбор администратора с явным предупреждением в интерфейсе** ("ответы резервной модели могут отличаться по качеству и стилю от основной"), а не скрытое поведение по умолчанию.

### Реализация
- В таблице `SystemSettings` (или `Bot`) добавить поле `modelName` (строка, например `gemini-2.5-flash`).
- В коде вызова `generateContent` убрать цикл перебора моделей; модель берётся строго из настройки бота (или глобальной, если у бота не переопределена).
- В UI админки — выпадающий список с доступными моделями (актуальный список моделей уточнить в документации Gemini API на момент разработки, не хардкодить устаревший список).

### Критерий приёмки
- [ ] Два одинаковых вопроса подряд с интервалом, достаточным для гипотетического "переключения", дают ответы в одном стиле/от одной модели (проверяется по полю `modelName`, логируемому в `ApiDiagnostics` вместе с каждым запросом).
- [ ] В админке видно, какая модель сейчас закреплена за каждым ботом, и её можно сменить.
- [ ] При отказе всех retry — явная ошибка клиенту, не тихий переход на другую модель.

## 1. Пустой текст ответа (Empty Response Bubble)

### Требование
1. Заглушка на случай пустого `content` — оставить как страховку (согласовано, симптоматический фикс адекватен).
2. **Добавить диагностику первопричины**: при каждом пустом ответе логировать в `ApiDiagnostics` — `finishReason`, был ли активен `fileSearch`, какая модель использовалась, длину запроса. Это нужно, чтобы отличить "пустой ответ из-за fileSearch на бытовой реплике" от "пустой ответ из-за safety-фильтра" — это разные проблемы с разными решениями.
3. После недели работы диагностики — проанализировать логи и решить, нужен ли отдельный фикс, помимо заглушки и решения проблемы №2 (RAG bypass), которое, вероятно, уже снимет часть случаев.

### Критерий приёмки
- [ ] Пустой ответ никогда не показывается клиенту без текста.
- [ ] Каждый случай пустого ответа модели оставляет запись в диагностике с `finishReason` и контекстом вызова.

## 2. Задержка на простые реплики (10–15 сек)

### Требование
Решать по шагам, от дешёвого к дорогому — не строить сразу сложный классификатор намерений вслепую.

**Шаг 1 — обязательная диагностика по этапам.** В `ApiDiagnostics` разбить время ответа на составляющие: время до первого байта от Gemini, число сделанных retry/переключений (после п.0 их не будет, но время retry той же модели тоже логировать), было ли использовано `fileSearch`. Без этого разбиения нельзя достоверно понять, что именно даёт задержку — сам факт RAG-поиска или что-то иное.

**Шаг 2 — проверить конфигурацию `tool_config` инструмента `fileSearch`.** Убедиться, что режим вызова инструмента — `AUTO` (модель сама решает, нужен ли поиск), а не принудительный `ANY`. Если сейчас стоит принудительный режим — это самый дешёвый и вероятный фикс, его нужно применить и измерить эффект до перехода к шагу 3.

**Шаг 3 — если после шага 2 задержка сохраняется, добавить дешёвый эвристический предфильтр** на сервере (без отдельного вызова модели-классификатора, чтобы не создавать новую задержку ради борьбы со старой): список типовых приветствий/благодарностей (регулярное выражение или простой словарь: "привет", "здравствуйте", "спасибо", "как дела", короткие сообщения до N символов без вопросительных конструкций по теме бизнеса) — на такие сообщения `fileSearch` tool не подключается вовсе для этого конкретного запроса.

**Шаг 4 (только если шаги 2–3 недостаточны)** — рассмотреть полноценный классификатор намерений отдельным лёгким вызовом модели. Не реализовывать сразу, только по факту недостаточности предыдущих шагов.

### Критерий приёмки
- [ ] Диагностика показывает раздельно: время retrieval, время генерации, число попыток.
- [ ] Ответ на "Привет" укладывается в целевое время (< 2–3 сек) после шагов 2–3.
- [ ] Решение о необходимости шага 4 принято на основе логов, а не заранее.

## 3. Фантомные RAG-источники (Ghost File References)

### Требование
1. **Архитектурный принцип: Google File Search Store — единственный источник истины**, без локального дублирования списка файлов клиента в собственной БД (устраняет саму возможность рассинхрона, а не только его следствия).
2. **Синхронное физическое удаление**: команда "удалить" в интерфейсе клиента = немедленный HTTP DELETE к Google Store API (`?force=true` для непустых документов) → интерфейс обновляется только после подтверждения успеха.
3. **Разделение файлов бота на "публичные" и "служебные"** через явный тег при загрузке (например, `visibility: internal` / `visibility: public`), вместо огульного исключения всех файлов бота из выдачи источников. Служебные файлы (системные инструкции, `Описание_ИИ.md`) — тег `internal`, никогда не показываются клиенту. Материалы экспертной базы бота (книги, методология) — тег `public`, могут законно показываться клиенту как источник с пометкой "из базы знаний ассистента".

### Реализация
- Убрать любую таблицу/поле в собственной БД, дублирующее список файлов клиента (если такое есть в текущей реализации — вывести из эксплуатации).
- При каждом открытии раздела "Библиотека бизнеса" — живой запрос к Google Store API за актуальным списком, не кэш.
- При загрузке файла ботом (через админку) — обязательное поле `visibility` (`internal`/`public`), сохраняется в metadata файла в Store.

### Критерий приёмки
- [ ] После удаления файла клиентом он не появляется в источниках следующего же ответа бота.
- [ ] Список файлов в UI клиента всегда идентичен списку в Store (нет расхождений при быстром обновлении страницы).
- [ ] Служебные файлы бота никогда не видны клиенту ни в списке файлов, ни в источниках; материалы базы знаний бота — видны, если помечены как публичные.

## 4. Карточка источников на нерелевантных ответах

### Требование
Блок «Источники из вашей Библиотеки бизнеса» показывается **только** при одновременном выполнении двух условий:
1. В ответе модели есть непустой `groundingSupports` (модель реально сослалась на конкретный текстовый фрагмент, а не просто "нашла что-то рядом" через `groundingChunks`).
2. Хотя бы один из этих источников относится к активным файлам пользователя (или к файлам бота с тегом `public`, см. п.3).

### Реализация
- В коде обработки ответа: проверять `groundingSupports`, а не только факт наличия `groundingMetadata`/`groundingChunks`.
- Пересечение с активным списком файлов выполнять после проверки первого условия, не вместо неё.

### Критерий приёмки
- [ ] Ответ "Здравствуйте! Чем могу помочь?" не сопровождается карточкой источников.
- [ ] Содержательный ответ, реально опирающийся на документ, сопровождается карточкой с точным указанием источника.

## 5. Дрейф меток времени (Timestamp Drift)

### Требование
Сообщение пользователя обязано сохраняться в БД с фиксацией `createdAt` **в момент поступления запроса на `/api/chat`**, до какого-либо обращения к Gemini API. Ответ бота сохраняется отдельной записью с собственной меткой времени по факту получения ответа.

### Критерий приёмки
- [ ] Метка времени сообщения пользователя не зависит от длительности ответа бота (проверяется временем ответа сервера на `POST /api/chat` — `createdAt` фиксируется до, не после, вызова внешнего API).

## 6. Диагностика сбоев и обработка сетевых ошибок

### Требование
1. **Health-check**: публичный эндпоинт `/api/health` для мониторинга доступности сервера (уже реализовано — сохранить).
2. **Автоматическое освобождение занятых портов** при перезапуске процесса (конфигурация деплоя/скрипта запуска).
3. **Клиент обязан разбирать JSON-тело ответа сервера даже при HTTP-ошибках (`4xx`/`5xx`)** и показывать пользователю точный текст проблемы из тела ответа, а не универсальную заглушку "сетевая ошибка".
4. Все технические ошибки (сетевые, таймауты, ошибки Gemini API, ошибки Store) — параллельно с сообщением пользователю пишутся в раздел "Диагностика" админки с полным техническим контекстом (см. также п.0, п.1 — единый формат записи в `ApiDiagnostics`).

### Критерий приёмки
- [ ] При падении бэкенда и последующем перезапуске порт не остаётся занятым "призрачным" процессом.
- [ ] Ошибка `DELETE /api/chat/history` (или любая другая) показывает клиенту содержательный текст из тела ответа сервера, а не общую "сетевую ошибку".
- [ ] Каждая ошибка присутствует в логе "Диагностика" админки с деталями, достаточными для отладки без доступа к серверу напрямую.

---

## Сводный чек-лист приёмки доработки

- [ ] Модель для каждого бота — явно закреплена в настройках, кросс-модельного фоллбека нет.
- [ ] Диагностика по этапам (retrieval / генерация / retry) видна в админке.
- [ ] Режим `fileSearch` tool — `AUTO`, задержка на приветствия устранена или явно объяснена логами.
- [ ] Google Store — единственный источник истины по файлам, удаление синхронно.
- [ ] Служебные файлы бота размечены и скрыты; публичные материалы бота законно видны как источник.
- [ ] Карточка источников показывается только при непустом `groundingSupports` + пересечении с активными файлами.
- [ ] Метка времени сообщения фиксируется до вызова внешнего API.
- [ ] Ошибки любого типа доходят до клиента как понятный текст и параллельно попадают в диагностику админки.
