# 📋 Реестр Системных Проблем и Архитектурных Требований ТЗ для KRB SaaS MVP (RAG Engine & UI)

Данный документ содержит систематизированный перечень проблем, выявленных в процессе эксплуатации и тестирования RAG-чата на базе Google Gemini API, а также формулировки жестких технических требований для внедрения в Техническое Задание (ТЗ) платформы.

---

## 1. Проблема: Пустой текст ответа бота (Empty Response Bubble)

* **Симптомы**: В пользовательском интерфейсе чата появляется плашка сообщения ассистента с именем и временем (`Test Bot 17:07`), однако поле самого ответа абсолютно пустое.
* **Причина**:
  - При запросах неконкретного/бытового характера («Как дела?») Google Gemini с подключенным инструментом `fileSearch` может возвращать структуры без символьного текста в `parts`.
  - В верстке `App.tsx` стояла проверка `msg.content && msg.content.trim() !== ''`. Если текста не было, блок текста полностью скрывался.
* **Требования к ТЗ**:
  1. **Резервирование текстового контента (Content Fallback)**: Серверная часть обязана гарантировать, что поле `content` в ответе API никогда не является пустой строкой.
  2. Если модель не вернула текстовых фрагментов, сервер автоматически подставляет понятный вежливый ответ-заглушку (*«Я на связи и готов проконсультировать вас по материалам вашей Библиотеки бизнеса»*).

---

## 2. Проблема: Задержки (15+ сек) и ненужный RAG-поиск на простые приветствия

* **Симптомы**: На бытовые реплики («Привет», «Здравствуйте», «Кто ты?») система задумывается на 10–15 секунд перед выдачей простой фразы.
* **Причина**:
  - Сервер безусловно передавал все хранилища RAG (`botStoreName` + `clientStoreName`) в вызов `generateContent` Gemini API независимо от смысловой нагрузки вопроса.
  - Gemini выполнять полнотекстовое векторное эмбеддирование по всем проиндексированным документам компании даже для слова «Привет».
* **Требования к ТЗ**:
  1. **Семантический маршрутизатор запросов (Smart Intent Router / RAG Bypass)**: Сервер перед отправкой запроса к Gemini должен классифицировать намерение пользователя.
  2. Если запрос является приветствием, благодарностью или общим вопросом без необходимости обращения к документам компании, инструмент `fileSearch` отключается. Ответ генерируется напрямую из базовой модели за < 1 секунды.

## 3. Проблема: Фантомные RAG-источники (Ghost File References)

* **Симптомы**: В карточке «Источники из вашей Библиотеки бизнеса» отображаются файлы, которые пользователь ранее удалил из личного кабинета, либо служебные файлы бота (`Описание КРБ_ИИ.md`).
* **Причина**:
  - Внешний Google File Search Store сохранял проиндексированные чанки (векторы) документов даже после их визуального удаления из интерфейса локальной БД, либо возвращал служебные файлы инструкции ассистента в общей выдаче `groundingChunks`.
* **Требования к ТЗ**:
  1. **Физическое удаление файла**: При удалении файла клиентом из Библиотеки бизнеса система выполняет обязательный HTTP DELETE запрос к Google Store API с параметром `?force=true`.
  2. **Пересечение активных источников (Active Store Intersection)**: Клиентский и серверный код обязаны фильтровать полученные `groundingChunks`: выводить источник в UI **ТОЛЬКО** в том случае, если имя файла присутствует в списке *активно загруженных документов пользователя*, и полностью скрывать системные файлы бота.

---

## 4. Проблема: Вывод карточки RAG-источников для нерелевантных ответов

* **Симптомы**: Под простым ответом бота «Здравствуйте! Чем могу помочь?» снизу выводится блок с перечислением всех файлов Библиотеки бизнеса.
* **Причина**:
  - Gemini API при включенном `fileSearch` всегда прикрепляет объект `groundingMetadata` с найденными близкими векторами, даже если модель **не использовала** эти данные для формулировки ответа.
* **Требования к ТЗ**:
  1. **Условие показа блока источников (Grounding Relevance Threshold)**: Блок «Источники из вашей Библиотеки бизнеса» выводится в UI **исключительно при соблюдении двух условий**:
     - Ответ модели содержит конкретные текстовые подтверждения/цитаты из документов (`groundingSupports` не пуст).
     - Найдено хотя бы одно совпадение с активными пользовательскими файлами.
  2. На простые реплики и общеэрудиционные ответы блок источников должен автоматически скрываться.

## 5. Проблема: Дрейф меток времени сообщений (Timestamp Drift)

* **Симптомы**: Время отправки сообщения клиентом фиксировалось тем же моментом, когда бот завершал свой длинный 15-секундный ответ.
* **Причина**:
  - Сообщение пользователя и ответ модели сохранялись в БД единым блоком **после** завершения работы функции RAG.
* **Требования к ТЗ**:
  1. **Мгновенное пред-сохранение (Immediate Pre-saving)**: Сообщение пользователя обязано фиксироваться в БД и возвращать точную метку времени (`createdAt`) **в момент физического поступления запроса** на сервер `/api/chat`, до вызова сторонних API.

---

## 6. Проблема: Блокировка сервера при падении прокси / конфликте портов («Сетевая ошибка при очистке истории»)

* **Симптомы**: Нажатие на кнопку «Очистить чат» приводило к вызову модального окна «Сетевая ошибка при очистке истории».
* **Причина**:
  - Конфликт фоновых процессов Node.js (`EADDRINUSE: 5001`), приводивший к падению бэкенда, и отсутствие в клиенте явной расшифровки HTTP-статусов ошибок при вызове `DELETE /api/chat/history`.
* **Требования к ТЗ**:
  1. **Диагностика и здоровье сервера**: Сервер должен содержать встроенный механизм автоматического освобождения портов и публичный эндпоинт доступности `/api/health`.
  2. **Информирование пользователя**: Клиентский код обязателен к разбору JSON-ответов с сервера даже при HTTP-ошибках (`4xx`/`5xx`) для вывода пользователю точного текста проблемы вместо общих сетевых заглушек.

---

## 7. Регламент и Стандарт Тестирования: Обязательная сквозная E2E-проверка (Level C UI/UX Verification)

* **Проблема**: Заявления о готовности задач на основе анализа серверного кода (Level A) или выгрузки структуры DOM (Level B) без реального подтверждения в интерфейсе браузера часто приводят к неработающим элементам UI у пользователя.
* **Регламентное Требование ТЗ**:
  1. **Категорический запрет на завершение задач без E2E**: Любые изменения в интерфейсе, модели, настройках или функционале считаются **НЕвыполненными** до тех пор, пока не проведена полная сквозная эмуляция поведения реального пользователя в браузере (Level C).
  2. **Обязательное доказательство в UI**: Проверка должна сопровождаться получением итогового снимка экрана (скриншота/видео), на котором отчетливо видны изменения прямо в действующем окне браузера.

---

## 8. Запрет Самодеятельности: Категорический Запрет на Вольную Интерпретацию и Запись Фейковых Данных

* **Проблема**: Допущение самовольных доработок (авто-генерация заменяющих фейковых данных / placeholders, мутация состояния БД без согласования) в ответ на уточняющие вопросы пользователя приводит к повреждению рабочих данных и сбою ключевого функционала.
* **Регламентное Требование ТЗ**:
  1. **Категорический запрет на несанкционированные доработки**: AI-ассистент **НЕ ИМЕЕТ ПРАВА** создавать фейковые записи-заглушки (placeholders), самостоятельно менять бизнес-логику инициализации БД (`initDefaults`) или делать предположения о требованиях пользователя без его прямого и явного поручения.
  2. **Принцип Явного Ответа**: На любой уточняющий вопрос пользователя («Почему в разделе X пусто?», «Где находится Y?») AI-ассистент обязан **ТОЛЬКО отчитаться по факту**, предоставив точную причину.
  3. **Обязательное Согласование Изменений**: Любое внесение изменений в схемы БД, скрипты инициализации, запись системных ключей или фолбэк-значений разрешено **ИСКЛЮЧИТЕЛЬНО после прямого утверждения** пользователем конкретного плана действий.
