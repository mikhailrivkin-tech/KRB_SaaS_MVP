# Техническое задание: ЛК с клиентским RAG-модулем

## 1. Цель проекта

Веб-платформа, где:
- клиент общается с AI-ассистентом (или несколькими ботами) через собственный интерфейс (без видимости native Gemini/NotebookLM UI);
- каждый бот имеет свой системный промпт и свою экспертную базу знаний (загружается администратором);
- клиент дополнительно сам формирует личную базу знаний (папки + файлы), которую бот учитывает вместе со своей базой при ответах;
- каждый клиент изолирован от других — видит только свои данные;
- есть закрытая админ-панель для управления ботами, техническими настройками (API-ключи) и памятью диалога.

Один API-ключ на каждый ИИ-сервис обслуживает всех клиентов. Изоляция клиентов — на уровне данных приложения, не на уровне ключей.

---

## 2. Роли

| Роль | Доступ | Функции |
|---|---|---|
| **Клиент** | Логин/пароль, видит только свой ЛК | Чат с ассистентом, управление своей базой файлов (папки, загрузка/удаление) |
| **Администратор** (вы/Игорь) | Отдельный логин/пароль, максимально защищённый вход | Управление API-ключами и системными настройками, обзор клиентов |

Многотенантность: несколько клиентов, у каждого — изолированная база файлов и своя история переписки. Клиенты не видят и не могут повлиять на данные друг друга.

## 3. Компоненты системы

### 3.1 Клиентский ЛК

**А. Модуль чата**
- Строка ввода запроса + окно диалога (история сообщений), с выбором бота (см. раздел 3.1.Г), если клиенту доступно несколько.
- Ответ формируется одним вызовом Gemini API с подключённым file_search tool — точная схема в разделе 4.
- История переписки сохраняется в БД, привязана к клиенту и к конкретному боту/диалогу (у каждого бота — своя отдельная история с этим клиентом, не общая).
- **Обработка сбоя API:** если вызов к Gemini завершился ошибкой (таймаут, лимит, недоступность) — клиент видит понятное сообщение в чате ("не удалось получить ответ, попробуйте ещё раз"), а не зависшую загрузку без объяснений. Техническая причина сбоя параллельно попадает в раздел "Диагностика" админки (см. 3.2).

**Б. Модуль базы знаний / "Библиотека бизнеса" (визуальный RAG-менеджер)**

Ключевой принцип: **Google File Search Store — единственный источник истины.** Приложение не хранит и не дублирует список файлов клиента в своей БД — при открытии раздела backend каждый раз живым запросом получает у Google актуальный список документов в store клиента и рендерит его в интерфейсе. Это исключает рассинхрон "у меня в ЛК файл есть, а по факту его уже нет" или наоборот.

- Древовидная структура папок, создаваемая самим клиентом (создание/переименование/удаление, вложенность) — папка реализуется как метка (тег) в метаданных файла при загрузке в store, а не как отдельная сущность в вашей БД.
- Загрузка файлов (drag-and-drop или кнопка): файл сразу уходит в Google File Search store клиента с меткой соответствующей папки; статус (загружен / индексируется / готов / ошибка) отображается по факту опроса статуса операции у Google.
- **Удаление — строго синхронная операция:** клиент нажимает "удалить" → backend немедленно вызывает удаление файла из Google store → только после подтверждения успеха интерфейс убирает файл из списка. Никакого "мягкого" удаления только в своём UI с файлом, оставшимся в Store, быть не должно.
- **Обработка ошибок индексации:** если Google вернул статус ошибки по файлу, клиент должен увидеть явную причину (текст ошибки) и кнопку "Повторить попытку", которая заново инициирует загрузку того же файла.
- При загрузке файл автоматически отправляется в Gemini File Search store, привязанный к этому клиенту.

**Важно — развилка по способу изоляции клиентов в Google File Search (уточнить перед стартом разработки):**
На стороне Google исторически существовало ограничение на число File Search Stores в одном проекте (было зафиксировано ~10 store/проект по документации конца 2025 года; актуальность на момент старта разработки нужно перепроверить в консоли Google, так как продукт активно меняется). Отсюда два варианта реализации, выбор — по факту проверки лимита:
  - **Вариант А (если лимит не мешает):** отдельный File Search store на каждого клиента — самая простая и надёжная изоляция.
  - **Вариант Б (если лимит критичен при большом числе клиентов):** один общий store (или несколько на группы клиентов) + обязательная метка `client_id` в метаданных каждого файла при загрузке, и фильтрация через `metadataFilter` при каждом поисковом запросе. Разработчику нужно гарантировать, что этот фильтр применяется на 100% запросов без исключений — это единственный барьер, не дающий данным одного клиента попасть в ответ другому.
- Папки в клиентском ЛК — не отдельная сущность вашей БД, а метка в метаданных файла внутри Google store (см. выше).

**В. Авторизация клиента**
- Логин/пароль, хэширование паролей (bcrypt/argon2), сессии/токены (JWT либо server-side sessions).
- Сброс пароля через email.

**Г. Множественные боты (системная база + личная база клиента одновременно)**

Цель: клиенту может быть доступно несколько ботов (например, "Маркетолог", "Юрист" и т.д.), у каждого — свой системный промпт и своя база знаний, которую загружаете вы (не клиент). При ответе бот одновременно опирается на две базы: свою (экспертиза бота) и личную базу клиента (его данные, цифры, документы).

Модель данных:
- Сущность **"Бот"**: `bot_id`, название, `system_instruction`, свой `file_search_store_name` (база бота — книги/методология, управляется через админку).
- Связь **"клиенту доступны такие-то боты"** (многие-ко-многим).
- При запросе backend передаёт в tool-конфигурацию сразу два store: store бота + личный store клиента (см. раздел 4) — технически это просто два имени в одном списке, лимит Google — до 5 store на один запрос, двух более чем достаточно.

Для MVP допустимо реализовать сразу с одним ботом по умолчанию, но структуру БД (таблица "боты" + связь с клиентами) заложить с самого начала, чтобы не переделывать её при добавлении второго бота.

### 3.2 Админ-панель

- Отдельный URL, недоступный из клиентского интерфейса (не должен быть виден в навигации или угадываться по паттерну).
- Авторизация: логин/пароль + **обязательная двухфакторная аутентификация (2FA, TOTP)** — учитывая, что здесь хранится доступ к платным API.
- Раздел "API-ключи":
  - Добавить ключ (с указанием, к какому сервису он относится: Gemini / Claude / др.)
  - Редактировать / деактивировать / удалить ключ
  - Ключи хранятся в БД **в зашифрованном виде** (например, AES-256, ключ шифрования — в переменных окружения сервера, не в коде и не в репозитории)
  - В интерфейсе ключ никогда не отображается полностью (маскируется, кроме момента ввода)
- Раздел "Память диалога" (настройки sliding window + суммаризации):
  - Поле "N последних сообщений" — сколько последних реплик диалога передавать в модель дословно (значение по умолчанию для MVP: 15).
  - Переключатель "Суммаризация старой истории" — вкл/выкл.
  - Если включено: поле "порог срабатывания" — после какого числа сообщений в диалоге запускать сжатие более старой части в резюме (по умолчанию: после превышения N в 2 раза).
  - Настройки применяются глобально на старте (одно значение N на все диалоги всех клиентов); в будущем можно вынести на уровень бота или клиента — закладывается как отдельное расширение, не требующее переделки структуры БД.
- Раздел "Боты" (реализуется по факту готовности MVP с одним ботом, но структура БД закладывается сразу):
  - Добавить/редактировать/удалить бота: название, `system_instruction`, загрузка файлов в собственную базу знаний бота.
  - Назначить, каким клиентам доступен какой бот.
- Раздел "Лимиты":
  - Простое ограничение на клиента — количество сообщений в минуту и/или в день (защита от случайного или намеренного злоупотребления, которое может привести к неожиданным расходам на API). При превышении — понятное сообщение клиенту ("превышен лимит сообщений, попробуйте позже"), не молчаливый сбой.
- Раздел "Диагностика" (особенно ценно на этапе отладки MVP):
  - Лог последних вызовов к Gemini API: время, client_id, bot_id, статус (успех/ошибка), текст ошибки при наличии, время ответа.
  - Цель — чтобы на этапе запуска можно было быстро увидеть, что именно пошло не так (таймаут, лимит, ошибка store), не залезая в серверные логи вручную.
- Раздел заложен с расчётом на расширение (позже — модели, лимиты, тарифы и т.д.), без необходимости переделывать структуру БД с нуля.

### 3.3 Backend / API-слой

- Прокладка между фронтендом и внешними AI-сервисами: фронтенд никогда не обращается к Gemini/Claude напрямую — все вызовы идут через ваш сервер.
- Причины: (1) API-ключи не должны попадать в клиентский код/браузер ни при каких условиях; (2) нужен контроль лимитов, логирование, биллинг по клиентам в будущем.
- Основные эндпоинты (укрупнённо):
  - `POST /chat` — принять вопрос клиента, выполнить RAG-запрос + генерацию, вернуть ответ
  - `POST /folders`, `PATCH /folders/:id`, `DELETE /folders/:id` — управление папками
  - `POST /files`, `DELETE /files/:id` — загрузка/удаление файлов (с прокидыванием в Gemini File Search)
  - `POST /auth/login`, `/auth/logout`, `/auth/reset-password` — для клиентов
  - `POST /admin/login` (с 2FA), `/admin/api-keys` (CRUD) — для админки, отдельное пространство эндпоинтов с усиленной проверкой прав

### 3.4 Хранилище данных

- **База данных приложения** (например, PostgreSQL): пользователи (клиенты + админы), боты и связи "клиент↔бот", история переписки (привязана к client_id + bot_id), зашифрованные API-ключи, логи доступа и диагностики. **Список файлов и папок клиента здесь не хранится** — это данные, за которые отвечает Google File Search Store (см. принцип "источник истины" в 3.1.Б); в своей БД хранится только `store_name`, привязанный к клиенту/боту.
- **Gemini File Search store(s)** — фактическое хранилище содержимого файлов и их метаданных (включая тег папки) для ретрива, единственный источник истины по составу базы знаний.

## 4. Модель ответа (сценарий генерации)

**Решение на текущий этап: только Gemini API (без Claude), один вызов на запрос.**

Схема — не два раздельных шага, а один вызов `generateContent` с подключённым `file_search` tool:

1. Клиент отправляет вопрос в чат.
2. Backend определяет, к какому store/сегменту данных относится этот клиент (SQL-lookup в своей БД: `client_id → file_search_store_name`).
3. Backend делает **один** вызов `generateContent`, передавая: системный промпт (сценарий), историю диалога (см. п. 4.1), вопрос клиента, и tool-конфигурацию с указанием store именно этого клиента.
4. Внутри этого одного вызова Gemini сам решает, нужен ли поиск, ищет релевантные фрагменты в указанном store и формирует обоснованный ответ — без ручной пересборки промпта на стороне backend.
5. Ответ (и ссылки на источники из grounding-метаданных) возвращается клиенту, сохраняется в историю.

Архитектура закладывается так, чтобы позже можно было заменить модель-генератор (например, на Claude через Vertex AI RAG Engine) без переделки клиентской части и базы данных — но на MVP это не реализуется.

**Проверено практическим тестом (текущий этап): File Search Tool работает на free tier без подключения биллинга** — создание store, загрузка файла, индексация и обоснованный ответ с цитированием источника отработали на бесплатном API-ключе. Индексация файлов при этом всё равно тарифицируется (см. раздел 6), но сам функционал доступен для разработки и тестирования без карты.

**Точная структура одного запроса (объединяет системный промпт, историю диалога, RAG бота и RAG клиента):**

```python
response = client.models.generate_content(
    model="gemini-2.5-flash",
    contents=[
        # история диалога (последние N сообщений, см. 4.1) + текущий вопрос
        {"role": "user", "parts": [{"text": "..."}]},
        {"role": "model", "parts": [{"text": "..."}]},
        {"role": "user", "parts": [{"text": "текущий вопрос клиента"}]},
    ],
    config=types.GenerateContentConfig(
        system_instruction="текст роли бота — заполняется в админке, раздел «Боты»",
        tools=[types.Tool(file_search=types.FileSearch(
            file_search_store_names=[
                "store_бота",      # экспертная база — грузите вы через админку
                "store_клиента",   # личные данные клиента — грузит он сам через ЛК
            ]
        ))]
    )
)
```

Это единственный вызов на каждое сообщение в чате — никакой ручной пересборки промпта из отдельно полученных фрагментов не требуется.

### 4.1 Управление историей диалога

У API нет памяти между вызовами — история подгружается заново при каждом сообщении, поэтому:
- Хранить полную историю диалога в БД (привязана к client_id).
- При формировании запроса передавать не всю историю целиком, а её ограниченное окно — количество последних сообщений (N) настраивается администратором через раздел "Память диалога" в админке (см. 3.2), а не жёстко зашито в коде.
- Суммаризация старой части диалога — включается/выключается и настраивается там же (порог срабатывания). Механизм: по достижении порога backend отдельным вызовом просит модель сжать более старую часть истории в краткое резюме, которое затем хранится в БД и передаётся вместо полного текста старых сообщений.
- Реализация самого механизма (подсчёт сообщений, обрезка окна, вызов суммаризации) — задача backend, оценочно некритичный по трудозатратам объём работы для MVP (десятки строк логики), но крайне желательно сделать пороги настраиваемыми через админку с самого начала, а не хардкодить, — это и заложено выше.

## 5. Требования к безопасности

- Админка: 2FA обязательна, отдельный домен/поддомен или скрытый путь, rate-limiting на попытки входа, логирование всех входов и действий с ключами.
- API-ключи: хранение только в зашифрованном виде, доступ к расшифровке — только у backend-процесса генерации запросов, не через обычный API чтения.
- **Важно про ротацию ключей:** File Search Store и загруженные файлы привязаны не к самому ключу, а к Google Cloud проекту, с которым ключ связан. Перевыпуск ключа в рамках того же проекта безопасен — доступ к store сохранится. Переключение на ключ от другого проекта/аккаунта сделает существующие store недоступными — это требует отдельного плана миграции данных, а не просто замены строки ключа в админке. Ключ от File Search также даёт доступ ко всем загруженным туда данным — хранить его нужно с особой строгостью.
- Изоляция клиентов: на уровне backend-логики — жёсткая проверка, что клиент А физически не может получить доступ к file store / истории клиента Б (проверка по clientId на каждом запросе, а не только на уровне UI).
- HTTPS везде, защита от стандартных веб-угроз (CSRF, XSS, SQL-инъекции — стандартный чеклист для веб-приложений).
- Резервное копирование БД (файлы клиентов и переписка — ценные данные).

## 8. Критерии приёмки MVP

### Клиентский ЛК

- [ ] Клиент логинится по логину/паролю, видит только свои данные.
- [ ] Клиент видит список ботов, заранее созданных администратором (у каждого — своё название, например "Маркетолог"), и может выбрать, с каким общаться.
- [ ] У каждого бота — отдельная, не смешивающаяся с другими ботами история переписки с этим клиентом.
- [ ] Клиент задаёт вопрос в чате и получает ответ, учитывающий и базу знаний бота, и его собственную загруженную базу.
- [ ] Раздел "Библиотека бизнеса": клиент создаёт иерархию папок, загружает файлы, видит статус обработки, удаляет файлы — все действия синхронно отражаются в Google File Search Store клиента (без рассинхрона между ЛК и Store).
- [ ] При ошибке индексации файла — видна причина и кнопка "Повторить попытку".
- [ ] При сбое ответа бота — понятное сообщение об ошибке, а не зависание.
- [ ] Клиент А не может увидеть ни файлы, ни историю переписки клиента Б ни при каких действиях в интерфейсе.

### Админка

- [ ] Отдельный вход по логину/паролю + 2FA, недоступен из клиентского интерфейса.
- [ ] Раздел "API-ключи": добавление/редактирование/удаление, хранение в зашифрованном виде, ключ не отображается полностью.
- [ ] Раздел "Боты": создание бота (название + системный промпт + собственная база знаний бота), назначение доступа конкретным клиентам.
- [ ] Раздел "Память диалога": настройка N последних сообщений и порога суммаризации.
- [ ] Раздел "Лимиты": настройка простого ограничения сообщений на клиента (в минуту/день).
- [ ] Раздел "Диагностика": лог последних вызовов к Gemini API с указанием ошибок, доступный без обращения к серверным логам напрямую.

## 9. Открытые вопросы к разработчику на старте

- **Проверить актуальный лимит File Search Stores на проект в Google Cloud Console** — от этого зависит выбор варианта А или Б в разделе 3.1.Б.
- Число ожидаемых клиентов на старте — влияет на то же решение.
- Необходимость email-уведомлений (сброс пароля, статус обработки файла).
- Ограничение длины/объёма истории диалога, передаваемой в контекст (сколько последних сообщений хранить без суммаризации) — зафиксировать конкретное число при тестировании реальной нагрузки.
- Момент перехода с free tier на платный биллинг Google — до выхода за пределы теста одним пользователем нужен платный тариф, чтобы не упереться в лимиты запросов в минуту/день при нескольких реальных клиентах.
- Разделение dev/prod окружений (отдельный тестовый Google-проект и отдельный ключ для разработки, чтобы не смешивать тестовые данные с боевыми).
- Если среди клиентов возможны физлица/ИП с персональными данными в загружаемых файлах — оценить риски по 152-ФЗ (данные уезжают на серверы Google за рубежом) и продумать пользовательское соглашение с явным согласием клиента на такую передачу.
